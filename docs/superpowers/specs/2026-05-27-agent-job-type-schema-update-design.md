# Agent Job Type Schema Update — Design

**Date:** 2026-05-27
**Status:** Approved (pending user review of this spec)
**Branch:** `fix/agent-job-type-schema-update`
**Scope:** Update the agent-related validation rules so they keep working when an upcoming version of `veeam-healthcheck` emits a new, platform-prefixed job-type vocabulary. Support both old and new formats during a transition window; warn once when legacy strings are detected.

## Background

Two validation rules in `src/lib/validator.ts` classify Veeam jobs by string-matching `JobType`:

- `validateAgentStandaloneUnsupported` (line 168) — fails when `jobSummary` contains a row with `JobType === "Unmanaged Agent"` and a positive count.
- `validateAgentPolicyGatewayRequired` (line 195) — warns when any `jobInfo` row has `JobType` in `{"EpAgentPolicy", "VmbapiPolicyTempJob"}`.

An updated `veeam-healthcheck` tool emits a new vocabulary. Confirmed against a user-supplied report (`Veeam Health Check Report_VBR_localhost_2026.05.27.041220.json`, generated by VBR 13.0.1.2067):

| Concept                      | Old strings                                            | New strings (platform-prefixed) |
| ---------------------------- | ------------------------------------------------------ | ------------------------------- |
| Managed agent backup         | `EpAgentBackup`, `Agent Backup` (jobSummary aggregate) | `Windows Agent Backup`          |
| Managed agent policy         | `EpAgentPolicy`, `VmbapiPolicyTempJob`                 | `Windows Agent Policy`          |
| Standalone / unmanaged agent | `Unmanaged Agent` (jobSummary only)                    | `Windows Agent Standalone`      |

Two consequential schema changes beyond the rename:

1. **Platform prefix.** New strings carry the agent's OS (`Windows Agent ...`); future Linux/Mac variants are expected to follow the same shape (`Linux Agent Standalone`, `Mac Agent Policy`).
2. **Standalone moves into `jobInfo`.** In the new format, unmanaged agents appear as named rows in `jobInfo` (e.g. `Unmanaged-WindowsAgents-VTESTVM03` with `JobType: "Windows Agent Standalone"`) — not just as a `jobSummary` count. That gives us named output for the affected-items list.

Without the change in this spec, an upload from the new healthcheck tool would silently pass both agent rules — a false-clean signal — because none of the old strings appear.

## Approach Considered & Rejected

- **Approach B — extend exact-match sets.** Add `"windows agent standalone"` etc. to the current `Set` literals. Smallest diff but every new platform (Linux, Mac) requires another code change.
- **Approach C — categorise during normalization.** Add `agentCategory: "standalone" | "policy" | "managed-backup" | null` to `SafeJob` / `SafeJobSummary` in `normalizer.ts`. Stronger typing but touches `types/domain.ts`, `normalizer.ts`, ~30 tests, for a single consumer (the validator). YAGNI for the current PRD.

The chosen approach centralises the naming knowledge in one tiny module without bleeding into normalization or types.

## The Classifier

**File:** `src/lib/agent-classifier.ts`

```ts
export type AgentCategory = "standalone" | "policy" | "managed-backup";

export interface AgentClassification {
  category: AgentCategory;
  legacy: boolean;
}

export function classifyAgentJobType(
  jobType: string | null | undefined,
): AgentClassification | null;
```

**Matching rules** — all comparisons are performed on `jobType.trim().toLowerCase()`:

| Category         | New-format pattern            | Legacy exact strings                   |
| ---------------- | ----------------------------- | -------------------------------------- |
| `standalone`     | `/^.+\s+agent\s+standalone$/` | `unmanaged agent`                      |
| `policy`         | `/^.+\s+agent\s+policy$/`     | `epagentpolicy`, `vmbapipolicytempjob` |
| `managed-backup` | `/^.+\s+agent\s+backup$/`     | `epagentbackup`                        |

Semantics:

- The pattern requires **at least one character followed by whitespace before `agent`**. A bare `"Agent Standalone"` without a platform prefix is **not** matched — Veeam's controlled vocabulary always emits a prefix, so anything missing one is more likely a name collision than a real agent job.
- `null` return means "this `JobType` is not agent-related." Callers branch on the result; there is no default category.
- `legacy: true` means the match came from the exact-string allow-list. The validator uses this flag to decide whether to emit the deprecation warning.
- `null` / `undefined` / empty / whitespace-only input returns `null`.

`managed-backup` is exposed even though no current rule needs it. It belongs to the same naming family and centralising it now means a future rule (e.g. "managed agent backups need a Gateway when targeting Vault") has one obvious place to ask.

## Validator Rule Changes

### `validateAgentStandaloneUnsupported`

New shape:

1. Filter `data.jobInfo` for entries whose `JobType` classifies as `standalone`. Collect their `JobName`s.
2. Filter `data.jobSummary` for entries whose `JobType` classifies as `standalone` **and** `Count > 0`. Sum the counts.
3. **If `jobInfo` matches exist:** return `status: "fail"` with `affectedItems` = the job names. Message uses the **count of named jobs** (`affectedItems.length`) for grammar agreement.
4. **Else if `jobSummary` count > 0:** return `status: "fail"` with `affectedItems: []`. Message uses the **summed `jobSummary` count**. This is the legacy fallback — old healthchecks only expose the aggregate count.
5. **Else:** existing pass result.

Message text remains the existing wording. Status stays `"fail"`. The only output-shape change is that `affectedItems` is no longer always empty for failures.

### `validateAgentPolicyGatewayRequired`

Straight substitution. Replace:

```ts
const POLICY_TYPES = new Set(["epagentpolicy", "vmbapipolicytempjob"]);
const matches = data.jobInfo.filter((job) =>
  POLICY_TYPES.has(job.JobType.trim().toLowerCase()),
);
```

with:

```ts
const matches = data.jobInfo.filter(
  (job) => classifyAgentJobType(job.JobType)?.category === "policy",
);
```

Title (`"Managed Agent Policies"`), status (`"warning"`), message, and `affectedItems` shape (job names from `jobInfo`) are unchanged.

## Deprecation Warning

Inside `validateHealthcheck()`:

```ts
let sawLegacy = false;
const noteLegacy = (cls: AgentClassification | null) => {
  if (cls?.legacy) sawLegacy = true;
  return cls;
};
```

The two agent rules pass classifier results through `noteLegacy()`. After the rules run, if `sawLegacy` is true, emit exactly one `console.warn`:

```
[vdc-vault-readiness] Legacy agent job type strings detected
(EpAgentBackup / EpAgentPolicy / Unmanaged Agent / VmbapiPolicyTempJob).
These will be removed in a future release once the updated veeam-healthcheck
tool is widely deployed. Please regenerate your healthcheck using the latest version.
```

**Why these choices:**

- **Once per `validateHealthcheck()` call, not once per match.** Three legacy rows produce one warning.
- **Validator-scope, not module-scope.** A module-level `hasWarned` flag would only fire on the first upload per page load; switching files in the same session would silently drop the warning.
- **`console.warn`, not a `ValidationResult`.** This is meta-information about the upload format, not a property of the Veeam environment under test. Adding a dashboard row would clutter the UI with something the end user cannot action without retooling.

## Scope & Non-Goals

**Out of scope:**

| Non-goal                                                        | Reason                                                                                                    |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Promoting `agentCategory` into `SafeJob` / `SafeJobSummary`     | No current consumer beyond the validator. YAGNI.                                                          |
| Surfacing the deprecation as a `ValidationResult` row or banner | Meta-info for the uploader, not an environment property. `console.warn` suffices until real users hit it. |
| Adding the user-supplied new-format JSON as a committed fixture | Customer-shaped data; synthetic in-test inputs are cleaner.                                               |
| Updating `veeam-healthcheck.example.json` to new format         | Keeping it on the old format means our fixture file actively guards the backward-compat path.             |
| Removing the legacy allow-list now                              | Deprecation window first. Deletion is a future commit once the new healthcheck tool is widely deployed.   |
| UI / chart / detail-sheet code changes                          | They render `JobType` strings as-is; new strings display correctly without code change.                   |
| `validateAwsWorkload`, version, encryption, SOBR rules          | No agent-type dependency.                                                                                 |

**Open questions:** none. Compatibility (transition window with deprecation) and platform coverage (pattern-based) are both pinned down.
